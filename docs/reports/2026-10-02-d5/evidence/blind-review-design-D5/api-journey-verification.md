# Principal API journey, assertion and sample plan

REQ-02/05/06/09 govern. api-journey-matrix.csv enumerates candidate endpoint contracts rather than claiming implemented routes. An implementation must bind each candidate to its actual route/version and identity provider boundary before separately authorized testing. Login, list/detail, profile and favorites reads/updates are the principal monthly SLO. Registration/admin/image/email are functional/authorization checks; registration is included in the proposed API load/performance plan without expanding the formal monthly SLO. Mail delivery completion stays excluded from API latency. No API was called.

## Data and consistency

Seed 10,000 synthetic identities, logical SQL 20 GB and images 100 GB with an explicit size histogram and database/object manifest. Padding bytes alone do not create representative indexes/hot-key contention: maintain profile/favorite/content cardinalities, row sizes, primary-key uniqueness, indexes and 9:1 read/write distribution. Test 2 GB SQL/10 GB image incremental data and a separate growth cardinality case without turning 1,000,000 registrations into traffic. Use two isolated subjects A/B, one admin, nonadmin role, expired/revoked token, opaque request/idempotency keys. Never use real names, email, credentials or image bytes in evidence.

After successful profile/favorite write W, immediately issue the writer's next read R through the public entrance, a new pooled connection and potentially another replica. R must observe W's committed version. Do not grant this with sticky sessions or a stale replica; primary read or verified causal watermark required. Check the returned subject and version, SQL commit sequence, one outbox event and uniqueness constraints. Concurrent update pair has explicit conflict/version behavior: at most one update per expected version; no silent lost update. Ambiguous commit: resolve the idempotency key against the fenced primary, return prior outcome or apply once; never blind retry.

## Load model and per-API samples

Candidate read mix totals 90%: login10%, list30%, detail25%, profile15%, favorites10%. Writes total10%: registration1%, profile4%, favorite add3%, favorite remove2%. Login is classified as read for this costing/load abstraction; provider auth side effects are counted separately. Shares are conditional, not supplied business facts. Admin update and image/CDN requests are separate traffic. Mix sum alone cannot establish actual usage or PV compatibility.

Plan three independently reset baseline runs: (N) 10 RPS for 30 measured minutes after 5-minute warmup (18,000 requests); (P) open-loop 100 RPS for exactly 900 measured seconds (90,000); (G) independent 1,000 RPS for 900 seconds (900,000). N's duration is a test proposal, not monthly normal-duty answer. Exclude warmup/ramp from reported interval but preserve them separately. Do not omit failed/shed requests from denominator. G may overload the initial design; it is recorded as a stress outcome and requires growth configuration/quote for acceptance. No generated load occurs in this task.

Expected N/P samples per route follow the mix: login1800/9000, list5400/27000, detail4500/22500, profile GET2700/13500, favorites GET1800/9000, registration180/900, profile PATCH720/3600, add540/2700, remove360/1800. G is P×10. N's sparse routes require a separate 10 RPS single-route 30-minute plan (18,000 samples) for each principal API, so aggregate percentiles cannot hide a slow route. Registration can use a resettable synthetic identity fixture, with vendor quota/rate/cost controls specified later. Single-route runs are separate from mixed 9:1 workload results, not pooled to manufacture a pass.

500 users is a separate closed-loop session model. Proposed sessions choose a route by the mix and pace to a controlled total target; record achieved RPS, simultaneous users, active requests, think time and dropped iterations separately. Little's law sensitivity: with 0.5-second mean service time, 100 RPS implies about50 active requests, not500. Neither pacing nor this illustrative mean is business input. Run open-loop arrival and 500-session models independently; record generator capacity so saturation is not confused with service success. Static image requests/PV remain separate; measure bytes, cache status and origin misses.

## Measurement and pass evidence

Clock each attempt from the external public DNS/TLS/edge boundary to complete validated response; preserve connection establishment and warm-connection strata. A successful status with wrong content/subject/version is a functional error. For each principal API and scenario report n, scheduled/started/completed requests, dropped arrivals, p50/p95/p99, error numerators, timeouts, 5xx, unexpected4xx/429, semantic assertion failures and expected denied-path4xx separately. Formal server-error fraction is <1% and p95≤500ms for normal and peak; overload/429 also counts as unavailable functionality and cannot disappear from SLO evidence. Show all-attempt latency with timeout right-censoring/deadline labels and successful-response latency separately. Do not call low samples statistically conclusive: proposed minimum1000 per route for a descriptive p95, bootstrap95% interval for p95 and binomial95% error interval. Threshold crossing/inadequate sample/CI straddling limit is inconclusive or failed as appropriate, never a fabricated zero-error guarantee. Full calendar-month external observations are required for actual monthly99.9, with interval coverage gaps explicit.
