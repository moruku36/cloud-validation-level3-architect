# Conditional IAM design — D01

iam-action-matrix.csv enumerates seventeen role categories per provider (51 rows), action proposals, conceptual resource scopes, conditions and future denied-path evidence. No resource identifier or live policy exists. Where an exact service permission/action membership could not be obtained, the cell explicitly says U; capability is defined, not guessed as a deployable permission. Exact custom policy syntax, required service dependencies, scope/condition support and effective grants need provider documentation and later authorized policy validation. Role names are planning categories, not named owners or assumed built-in role memberships.

## Enforcement semantics

AWS: explicit deny overrides allow; identity/resource grants combine and boundaries/SCPs can restrict them. Propose deny non-TLS object access and unintended buckets/prefixes; deny IAM policy/role mutation, arbitrary PassRole and destructive key actions to workload/CI. Scoped grants must use actual supported resource types when later authored. ecs:RegisterTaskDefinition requires wildcard resource per retrieved documentation; isolate build registration identity with protected OIDC subject, restrictive pass-role and reviewed deployment manifest. Do not attach runtime permissions to execution/image-pull identity. MFA human sessions do not apply identically to federated CI: use OIDC subject/audience controls instead. Region constraints require exceptions for global APIs reviewed separately; not a residency proof.

Azure: Actions/DataActions distinguish control/data access. NotActions/NotDataActions subtract from one grant and are NOT explicit deny against another role assignment. Do not claim a generic user-created deny policy: Azure manages deny assignments; inspect inherited/system deny availability if later authorized. Proposed denial is no broad Owner/Contributor/DataOwner grants, scoped custom allow roles, separate managed identities and no shared storage keys, plus resource/data/network policy where supported. Storage key listing must be excluded because it bypasses intended data access. ABAC applies to supported actions/attributes only; blob prefix or case/version constraints unsupported by IAM require a broker/application allowlist. PIM/Conditional Access/MFA availability/licensing U and belongs in quote; no automatic JIT entitlement assumed.

GCP: use separate service accounts and custom role permissions; short-lived federation for CI; only approved runtime account actAs. Omit setIamPolicy, service-account key creation and token impersonation from all ordinary roles. Deny policy is additional protection only for permissions on the supported deny list, not all permissions. Resource name/tag/time conditions are service/action-dependent; do not claim deny/condition support before checking it. Storage get/create/delete scoped to distinct buckets or managed folders when supported; list leakage/prefix limits require broker review. IAM auth/Cloud SQL connect permission does not grant PostgreSQL row/table privileges.

## Application and SQL grants

API database role: SELECT approved content; SELECT/INSERT/UPDATE own profile/favorites via server-side subject checks and database row security where validated; insert outbox atomically. No superuser/DDL/bulk export. Content role changes approved content only. Worker reads/claims outbox and updates delivery status via bounded function. Deletion role executes authorized case-specific SQL function, no arbitrary SQL; restore SQL admin is quarantine-only. Migration identity runs reviewed schema migration during approved window, has no standing production credential; add to pool operations 10 allowance, separate deploy approval. Key-use privilege (decrypt/encrypt on app key) goes to runtime/service encryption path only, not key administrator; each secret has per-role read grant, no secret list/write for workload. Auth admin deletion/export uses isolated adapter for approved cases; managed identity vendor API permissions remain U until vendor chosen.
