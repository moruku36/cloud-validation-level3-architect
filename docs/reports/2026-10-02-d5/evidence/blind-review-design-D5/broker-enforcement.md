# Manifest, version and restore-destination enforcement

Conditional desk design for I08 release, I10 restore, I12 deletion and I15 copy roles. Cloud IAM cannot generally inspect arbitrary signed case manifests, application versions or restore destinations. Enforcement is a broker plus separate identities and immutable artifacts, not an invented provider IAM condition. Exact action/resource/condition support remains U where inherited matrix marks it U. No credentials or policy were deployed.

## Trust and state

Approval artifact contains schema version, case/change ID, issuer and independent approver role IDs, created/expires times, nonce, purpose, environment, exact source/destination resource references, allowed object generation/version IDs, operation list, digest, runtime identity, network path, region and resource/pool/replica budgets. Actual identifiers are absent from this packet. Canonical serialization rejects duplicate keys, unknown fields, ambiguous unicode/path traversal, wildcard resources, mutable image tags and unsupported API operation. Verify signature against pinned approver key, certificate/key validity, source digest and current approval ledger status; approval and key rotation locations/retention remain owner-open. Build cannot sign production approval; approver cannot alter signed content without a new independent approval.

Broker privately authenticates ordinary executor, authorizes purpose/role/environment, resolves a protected immutable approved artifact by digest (never caller-supplied remote URL), checks one-time nonce/expiry and marks an atomic execution record. Max proposed execution token10min, smaller approved job deadline when needed; long deletion job resumes idempotent per-object work under new scoped authorization, not an immortal admin credential. Invalidate on change revocation, loss of approved identity or effective-grant drift. TOCTOU protection pins observed provider resource generation/etag where supported and verifies latest safe state before each action; unsupported preconditions mean pause/reinventory/reapprove rather than assume atomic provider support.

Broad cloud write/restore/delete privileges belong only to isolated broker service identities, not release operator, ordinary CI, executor laptop, content/API worker or privacy steward. Broker is separate from public app deployment and its approved image; changing broker code/allowlists/policy requires independent platform/security approval. Broker holds no arbitrary cloud shell or user-defined scripts. Network egress allowlist uses approved service endpoints; no client redirect/URL destination. Secret/key-use references are role-specific; caller cannot choose impersonation/PassRole/actAs target. Service-level/network constraints are enforced only where documented; unsupported precision stays a validation blocker. Broker audit writes independently to the restricted receipt store and cannot erase or change audit retention.

## Operation-specific checks

Release: exact immutable OCI digest plus reviewed task/revision/config digest; compare full before/after manifest, including runtime/execution identity, ingress, network, env/secrets, region, scaling/concurrency/DB-pool/permit maxima and rollback digest. Refuse unexpected changes, parallel release, arbitrary image registration/pass role, new public origin or tagged revision, shell overrides and unapproved increased resource budget. The broad provider update permission cannot protect those fields by itself. Broker reads back normalized deployed settings/digest later and reconciles; unknown readback blocks next stage. Task definition registration wildcard-resource capability is isolated; no wildcard execution right reaches ordinary CI.

Restore: approved source/point and destination in dedicated quarantine account/subscription/project boundary with no customer route, no prod app identity, no shared credentials and private network only. Destination labels alone are not a security boundary. Broker creates/restores through fixed destination mapping; rejects in-place production restore, caller-provided existing destination, geography/key/network changes and copy export to arbitrary object store. Restore identity cannot update edge/DNS/production secret pointers or grant IAM. Publication is a different broker operation under two independent approvals, recovery-ledger-predicate.md and principal verification; no `restore complete` event grants it. Existing provider restore/clone action destination semantics U must be documented and denied-path tested later before accepting this implementation.

Deletion: authorized case comes from immutable approved ledger; exact SQL stored function by case and version/generation object allowlist. No caller-supplied SQL, prefixes, regex, whole bucket/container or version wildcard. Fencing withdraws user writes and linked content uploads; a new matching version after manifest creation pauses/inventories/reapproves, preserving withdrawal rather than widening scope silently. Enumerate current/noncurrent versions, markers, replica versions, multipart upload IDs and cache/token populations separately. Delete marker does not count as erased prior bytes. Multipart abort requires exact case-linked upload ID; no orphan bulk delete. Signed manifest changes, out-of-scope keys, alternate replicas or unapproved retention exception are rejected. Vendor auth/mail deletion adapter has separate request/job receipts and remains U until vendor/recipient boundary established.

## Escape-path inventory and future rejection assertions

|Attempt|Required rejection/evidence predicate|
|---|---|
|Alter digest/version/destination after approval; replay nonce; expired or self-signed manifest|No provider action; denied reason/signature/nonce state in independent audit; changed artifact requires fresh approval|
|Direct cloud console/API via executor/CI; alternate pipeline/tag/origin; broker code replacement|No effective cloud grant except broker; denied direct action; inventory all inherited/resource/organization grants and runtime impersonation paths|
|AWS broad PassRole, resource policy/grant, build-register wildcard, execution identity confusion|Unapproved role/resource grants absent or supported deny applies; positive approved exact role works, unrelated identity rejected; actual dependencies not guessed|
|Azure inherited Owner/Contributor/DataOwner, listKeys/shared key, SAS, alternative managed identity|Remove broad effective grants, disable shared-key bypass where supported and account for SAS issuers; NotActions alone does not deny. Any unremovable inherited grant keeps acceptance HOLD|
|GCP inherited project/folder role, setIamPolicy, token creator/key, actAs, signed URL|No ordinary mutation/impersonation capability; check service-account grant chains and approved URL signer; deny only supported permissions. Unsupported deny cannot be assumed|
|Quarantine label spoof, production network/identity, public endpoint or publication without replay|Destination generation/path/identity match; denied destination and routing updates; no principal customer fetch possible from quarantine|
|Deletion version race/case scope widening/unrelated multipart or audit purge|No widened deletion; case paused and subject remains withdrawn; independent receipt retained; synthetic unaffected subject/version still exists|
|Emergency escalation while approver/audit unavailable|No fail-open broker grant; incident scoped approved session expires and cannot approve own loss/publication or erase audit|

Later authorized evidence must include complete effective-policy graph, all cloud direct and alternate grant paths, SQL role/function grants, broker immutable version, positive exact operation and each negative fixture above. A malicious broker identity or cloud administrator can bypass an application allowlist: organization/admin break-glass controls, dual approval and independent auditing remain necessary owner/source/live acceptance conditions. Do not describe the broker as security proof merely because its design is written.
