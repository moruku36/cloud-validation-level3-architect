# Conditional adoption decisions

All decisions below are proposals for all three providers on identical business constraints; no cloud is selected. Assess feature/region availability and quote before approval. This document supplies the missing adopt/reject/alternative/revisit reasoning; provider mappings remain in architecture-options.md.

|Topic|Proposed choice and why|Rejected for initial design; tradeoff|Alternative and revisit trigger|
|---|---|---|---|
|VM|Do not adopt initially: one infrastructure specialist and daytime coverage make guest patching/replacement an avoidable responsibility.|VM autoscaling groups remain feasible; direct host access gives tuning/control but requires image lifecycle, patching, zone balancing and recovery automation.|AWS EC2 ASG, Azure VMSS, GCP managed instance group: use if kernel/native agents, persistent host dependencies or measured platform limitations require it; price two-zone minimum and labor.|
|Containers|Adopt immutable stateless OCI image, health/readiness, graceful draining, 2 minimum replicas and bounded scale. Same app artifact helps migration and staged rollback.|Self-managed container hosts add OS/orchestrator work; image alone does not prove portability or adequate throughput.|ECS/Fargate, Container Apps, Cloud Run; verify runtime/timeout/VPC/region/zone guarantees separately. Revisit on measured connection/cold-start limits, unsupported networking or higher sustained CPU cost.|
|Serverless functions|Reject request-per-function decomposition initially: principal transactions/auth/outbox need one coherent deploy/consistency boundary; many functions add permissions and tracing complexity.|Cold starts, execution/request limits, SQL connection fan-out and mail retry behavior require proof; serverless is not intrinsically cheaper or available.|Lambda/API Gateway, Azure Functions, Cloud Run functions for bounded asynchronous jobs; adopt only if independent lifecycle/event demand is demonstrated and cost/pool isolation improves. Cloud Run/Container Apps remain serverless container runtime candidates.|
|Kubernetes|Reject initially: no production Kubernetes experience, six-person team and daytime coverage; current app does not require operators/service mesh/custom scheduling.|Managed EKS/AKS/GKE still require workload policy, upgrades, node/system components, networking and incident skill; Autopilot reduces portions without removing duties.|Managed Kubernetes if many independently deployed services, operator-only workloads or portability needs outweigh measured extra platform/labor floor; require training, staffing and full quote first.|
|SQL|Adopt managed PostgreSQL: transactions and constraints couple profile/favorites/outbox; read-after-write is required for the writer's next request. Read own writes from primary; replicas cannot serve this path without causal watermark checks.|Single-zone SQL reduces price but is rejected against current single-AZ objective pending explicit accepted change; managed HA still needs fencing/pool proof.|Managed HA primary+standby, 2 vCPU/8 GiB conditional base; scale vertically/index/query first, read replica only for stale-tolerant list reads. Revisit at 70% sustained CPU/IO or connection budget, or sharding need measured under growth.|
|NoSQL|Reject as authoritative initial store: current data model needs relationships, uniqueness and transactional outbox; no proven key access/partitioning advantage.|DynamoDB, Cosmos DB, Firestore have distinct consistency/transaction/region/cost semantics; substituting one does not preserve SQL behavior automatically.|Use as derived cache/read model if observed SQL load and stable keys justify duplicate data, deletion reconciliation and rebuild cost; require current vendor limits/prices and schema/consistency validation.|
|Ingress/CDN/WAF|Adopt one controlled public TLS ingress, origin isolation, WAF rules with monitor-then-enforce change, image CDN; protect admin separately.|Direct public DB/origin rejected; unmeasured WAF blocks can lower SLO, global edge/control-plane may conflict with expanded data boundary.|Regional ingress/private object signed reads if global edge geography is unacceptable; measured cache benefit and WAF false-positive rate determine use. Baseline 1 LB + 1 WAF policy; no residency claim for edge.|
|Zone resilience|Adopt two-zone app and managed zone-resilient SQL as proposal for single-AZ failures; surviving capacity must cover 100 RPS.|App across zones with single-zone DB remains a single data failure boundary; HA does not protect logical corruption or region loss.|N+1 measured application capacity; increase warm floor if scale recovery misses budget. Region/provider feature semantics must be sourced before approval.|
|Backup/PITR|Adopt encrypted managed backups, proposed 7d PITR and backup age≤35d; object version inventory and deletion replay quarantine.|Versioning/soft delete alone is rejected as proof of independent backup; immutable retention cannot silently delay valid deletion.|Daily backup plus hourly durable deletion manifest, separate Japan backup destination and restore evidence. PITR lookback and object replica policy need owner approval. Revisit if loss window/restore time or delete proof fails.|
|Regional DR|Conditional cold rebuild from approved separately protected Japan copy; no 30m/5m promise for region loss.|Warm regional standby is deferred: doubles portions, adds transfer/keys/identity/DNS and unapproved recurring cost; same-region copy cannot survive region loss.|Warm Osaka/Japan West standby only with approved RTO/RPO, verified service geography and extra budget; conditional cold target decision+24h, unproved. No automatic cross-region failover without data-loss authority.|
|Identity/mail|Adopt managed identity and transactional outbox worker conditionally, to reduce password/delivery operations.|Treating a vendor as Japan-resident by product label is rejected; recipient copies and global identity dependencies can defeat geography/SLO.|Self-hosted identity/mail increases security and labor responsibility; choose only after location/contract evidence and staffed operations. Auth outage stays inside principal SLO.|
|IaC/CI/state|Adopt environment-separated private state, OIDC short-lived deploy identity, immutable digest and independent production approval.|Long-lived CI keys and CI approval of its own production change rejected; state may contain secrets and needs restricted audit/backup/deletion.|State vendor/CI vendor U. Provider-native deployment alternative if validated export/rollback and environment separation survive. Revisit at denied-path or portability failure.|

Portability plan: export PostgreSQL schema/data and count/checksum; export object/version inventory and hashes; export allowed identity attributes without password/session assumptions; rebuild secret references and provider-specific ingress/queue/IAM; staged DNS cutover with rollback. Cost includes temporary duplicate compute/SQL/storage, migration bytes and labor. The container artifact does not make these dependencies portable. No rehearsal performed.
